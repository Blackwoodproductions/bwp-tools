# Verification rows

Source: `app/domain/content_publishing/bron/verify.py` in cade-service (the authority; "08 §4 as a command") and `docs/premium-seo-migration/program/runbook-cutover.md` §3. The code has **18 rows**, plus a synthetic **row 0** ("cut over") that answers alone when the record is not at `finish`. Each row scores `PASS`, `FAIL`, `SKIP` (rescue skips row 9) or `MANUAL` (CADE cannot see it; a person checks). `MANUAL` is not a failure and does not lock the site. Where no remedy is documented the row says "escalate to the migration lead"; do not improvise one.

**WAF-prone rows (4, 5, 17).** These probe the site's old addresses without following redirects and expect a 301. A Cloudflare/WAF-fronted site can answer CADE a block and score them `FAIL` although a browser gets the right 301. Before acting on one of these, open the listed address in a browser. Current code reads these redirects through CADE's proxy ladder (direct, then proxies); the runbook's "direct httpx" wording is older, so false FAILs are less likely than it says but still possible. Row 4 also reads each post's REST meta through the same ladder.

| # | Row | Checks | Typical FAIL cause | Do this |
|---|---|---|---|---|
| 0 | cut over | The record is at `finish` and has a bwp domain id | "not cut over: <stage>" | Finish the runbook (`wp-migration:site`), then verify |
| 1 | content served from the site | A migrated post and a Resources post answer 200 with the same body to a browser and to Googlebot; the site's outbound log shows no feed call (MANUAL unless CADE has that log) | A cache or plugin serves bots a different copy; page not 200 | Open the URL as a browser, compare with a bot fetch; otherwise escalate to the migration lead |
| 2 | a Resources post per linkable row | Every page in seo-service's link context has a tracked Resources post, and no post exists for a row with no page | "no Resources post for [ids]": `prepare` did not mint it; seo-service has no link context | Escalate to the migration lead: fixing this needs a rollback (`wp-migration:site` → Rollback) and a re-run of the stages, which is the lead's call |
| 3 | placeholders gone | No legacy placeholder page is left on the site (re-check after 24 h) | "N placeholder page(s) left": `remove` did not delete them | Escalate to the migration lead: fixing this needs a rollback (`wp-migration:site` → Rollback) and a re-run of the stages, which is the lead's call |
| 4 | legacy paths forward, exact **(WAF-prone)** | Each `cade_legacy_paths` entry on each post answers one 301 straight to the post | Another redirect plugin or host rule answers first (`X-Redirect-By: none`); CDN served a stale copy; WAF block | Open the address in a browser first. If it truly does not forward: delete the other plugin's rules for the listed addresses (e.g. "301 Redirects" → Manage Redirects) and flush the host cache (Flywheel: Advanced → Flush cache), then re-verify. Row detail carries the hint text |
| 5 | legacy paths forward, by id **(WAF-prone)** | `/x-<id>/`, `/x-<id>bc/` and `/<id>bc/` each 301 to the article or Resources post | Same as row 4 | Same as row 4 |
| 6 | footer present and recognisable | Homepage HTML carries `seo-automation-spacer` and `class="seo-sub-nav"`, no href to `<label>.php` (CC01) and no `[DMB01]` comment | Footer not rendered server-side (cache, theme); CC01/DMB01 present, which makes the crawler flip `wp_plugin` to 0 | Flush the site cache and re-verify; if the CC01/DMB01 marker is named, escalate to the migration lead |
| 7 | legacy listener | `/<label>/?Action=checkWPfiles` (four variants) answers 2xx with the exact OK line (50+ bytes, no "Not Found"), and `?Action=version` reports 46 | cade-seo's listener is off, cached or blocked | Escalate to the migration lead |
| 8 | crawler verdict | services-app's dry-run crawl: verdict OK, branch ok, all checks true, predicted status 2, no CC01/UD12/UD13/UD18/UD22 intent. On FAIL, escalate to the migration lead |
| 9 | write-back landed | seo-service's stored `url` and `resourcesUrl` match the posts CADE minted (`SKIP` on the rescue profile) | Write-back to bwp did not land; on a non-matching host, seo-service rejects the address | Re-run `finish`; escalate to the migration lead if it recurs |
| 10 | link tree rendered | Every Resources post's last link-sync verdict is green and its link tree is on the page | "the last link sync read it red/never" | Run `wp-migration:link-sync`: it re-reads every page it last read red |
| 11 | keyword_mapping links rendered | Each mapped keyword is linked on its Resources page | A keyword left unlinked, usually the same cause as row 10 | Run `wp-migration:link-sync`, then re-verify |
| 12 | no feed dependency left | Premium SEO is not running. `MANUAL` on a state-A site: its emptied plugin entry is still listed active | "Premium SEO running": it was not switched off or came back | Switch Premium SEO off in wp-admin (`remove` is refused at `finish`). If it still runs afterwards: escalate to the migration lead: fixing this needs a rollback (`wp-migration:site` → Rollback) and a re-run of the stages, which is the lead's call. On MANUAL, nothing to do now; only WP-CLI can unlist the entry (known gap) |
| 13 | publication rows | Every minted post has its post id, URL and bwp write-back; every Resources post has its hashes and a verdict | "publication <kind>/<id> lacks ..." | Re-running `finish` re-writes the URLs to bwp, so it fixes only a missing bwp write-back (`lacks bwp_written_at`); then `wp-migration:link-sync`. For "lacks post id / URL / hash" failures, escalate to the migration lead |
| 14 | schedule | One `(wordpress, bron)` row and no `(seomoney, bron)` row; the full profile also wants it enabled and publishing (rescue accepts disabled) | No row minted, or a `(seomoney, bron)` row left | Escalate to the migration lead |
| 15 | bwp status 2 | bwp status is 2 (hold it 48 h) | Status not 2 | Escalate to the migration lead |
| 16 | wp_plugin = 1 | bwp `wp_plugin` is 1 | Still 0: the crawl has not flipped it, or CC01/DMB01 flipped it back | Confirm the operator clicked **Reconnect**; otherwise escalate to the migration lead |
| 17 | PHP-style addresses forward **(WAF-prone)** | `/<label>.php?Action=1|2&k=x&PageID=<id>` 301 to the article / Resources post | Same as row 4 | Same as row 4 |
| 18 | images on the site | No migrated post still loads an image from the image host | `prepare` could not move an image; `finish` refuses while one is left | Re-run `finish`: it re-sideloads every image still on the host |

Two known, non-actionable results: the `PageID` form at the site root (`/?Action=1&k=x&PageID=<id>`) is not forwarded by design (a 200, not a 404), and a member of an Agentic package gets no post and its own old address is not forwarded. Neither is scored.
